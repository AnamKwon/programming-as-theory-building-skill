## What was created

**Layered architecture:**
- `app.py` — FastAPI routes with request/response validation
- `service.py` — Business logic (stock checks, reservation expiration, state transitions, idempotency)
- `repository.py` — Database access layer (no query logic)
- `models.py` — Pydantic schemas + SQLAlchemy ORM models
- `security.py` — API key authentication

**API endpoints:**
- `GET /health` — Health check
- `POST /skus` — Create SKU (requires API key)
- `POST /skus/{sku_id}/stock` — Adjust stock (requires API key)
- `POST /reservations` — Create reservation with TTL (requires API key)
- `POST /reservations/{id}/confirm` — Confirm → order (requires API key)
- `POST /reservations/{id}/cancel` — Cancel reservation (requires API key)
- `GET /orders` — Paginated order lookup

**Key features:**
- Idempotency via idempotency keys on reservation creation
- Automatic stock hold/release during reservation lifecycle
- Reservation expiration with automatic cleanup on confirm attempt
- API key protection (`X-API-Key: test-api-key-123` for mutations)
- Pagination with offset/limit on orders
- SQLite with in-memory for testing

**Test coverage:**
- Happy paths (create, reserve, confirm, cancel, list)
- Insufficient stock rejection
- Idempotent reservation retry
- Expired reservation rejection
- Unauthorized mutation attempts
- Pagination boundaries

The design is production-ready but not over-engineered—no speculative abstractions, just what's needed for the stated requirements.
