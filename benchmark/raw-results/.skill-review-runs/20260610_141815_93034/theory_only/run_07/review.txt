**Theory:** This is a FastAPI + SQLite inventory-reservation/order service. Domain maps: SKUs → stock(available/reserved) → reservations(pending/confirmed/cancelled/expired with TTL) → orders(paginated). Invariants: stock availability gates reservations, idempotency keys dedupe reservations, expiration releases reserved stock, mutations require API key.

Key findings from inspection:
- All tests pass (24) but only with `src` importable; plain `pytest` per README needs `pip install -e .` first (no `pythonpath` config).
- **Confirm never consumes reserved stock** — after confirm, `reserved` stays inflated permanently (`repository.confirm_reservation` only flips state + creates an order; no stock mutation).
- **Cancel has no guard against confirmed reservations** — cancelling a confirmed reservation releases stock again and can drive `reserved` negative while the order persists.
- Confirm-idempotency matches an order by `sku_id` + state only (no reservation→order FK), so a repeat confirm can return the wrong order.
- Lazy expiration runs only inside `confirm_reservation`; `create_reservation` doesn't sweep first, so expired-but-unswept reservations cause false `InsufficientStock`.
- Dead code: unused `pydantic-settings` dep, unused `JSONResponse` (app.py:2), unused `Optional` (models.py:3); committed `commerce.db` state artifact.
